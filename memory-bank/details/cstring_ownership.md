# CString の所有権・容量・寿命（Linux版EU4 v1.37.5、2026-11-21調査）

対象は `CTextSprite::SetText` の第1引数（SysV x86-64 の `rdx`、`CString const&`）が指す `CString`。根拠は EU4 バイナリの逆アセンブル（`objdump -dC` / `readelf -Ws`、アドレスは v1.37.5 のファイルオフセット相当の仮想アドレス）と、既存の実機ログ・トレースである。可変長置換はこの調査では実装していない。

## 結論の要約

- `CString` は libstdc++ の `std::__cxx11::basic_string<char>` と同じ 32 バイトのレイアウトを持つラッパーであり、文字列バッファを自分で所有する。
- 容量はオブジェクトの +16 にある共用体で決まる。データポインタが自オブジェクト +16 を指す場合は SSO（内蔵バッファ、容量15バイト＋終端NUL）、それ以外の場合はヒープ確保で、+16 の先頭8バイトが確保済み容量（`size_t`）である。
- 現在の `settext_hook.d` は先頭16バイトしか読まないため、容量は現行フックでは判定できない。可変長置換を安全に行うには、まずヘッダ読み取りを32バイトへ広げ、容量を確認する必要がある。
- `SetText` 自体は引数の長さフィールドを使わず、`strlen(data)` で内容を自オブジェクト内の文字列へコピーする（`_M_replace`）。引数 `CString` の寿命は呼び出しの間だけ必要で、戻り後に `SetText` 側がポインタを保持することは、少なくともこの関数の先頭処理では確認されなかった。
- 容量以内の可変長置換は、長さフィールド（+8）と終端NULを合わせて更新すれば原理的には可能と判断する。容量を超える置換は、EU4 自身の文字列確保処理をフック側から安全に呼べることが証明できていないため、引き続き実装しない。

## レイアウトの根拠

| オフセット | 内容 | 根拠 |
|---|---|---|
| +0 | `char*` データポインタ | 既存フックの実機動作、`CString::operator==` が `(%rdi)` / `(%rsi)` を `bcmp` の対象に使うこと |
| +8 | 長さ（`size_t`、ただし `GetSize` は下位32ビットを返す） | `CString::GetSize`（`0x254c3ee`）が `mov 0x8(%rdi),%eax` のみ。`operator==` は +8 同士を比較してから内容を比べる |
| +16 | 共用体：SSO時は `char[16]` の内蔵バッファ、ヒープ時は確保済み容量 | デフォルトコンストラクタとデストラクタの下記動作。`CString::_NullString` は32バイトの `OBJECT` |

- デフォルトコンストラクタ `CString::CString()`（`0x254b128`）：+0 に `this+16` を格納し、+8 を 0 にし、+16 の先頭バイトを 0 にする。これは libstdc++ `std::string` の SSO 初期状態そのものである。
- デストラクタ `CString::~CString()`（`0xd95742`）：+0 が `this+16` と異なる場合だけ `operator delete` を呼ぶ。つまりヒープバッファはオブジェクトが所有し、破棄時に解放する。SSO 時は解放しない。
- コピーコンストラクタ（`0x14f37ac`）は元の +0 を読み、`std::string` の `char const*` コンストラクタで新しい所有バッファを作る。ムーブ代入（`0x14f3ada`）は `std::string` のムーブ代入へ委譲する。コピーでバッファを共有しない。
- `CString::CString(char const*)`（`0x254b1c2`）と `CString(char const*, int)`（`0x254b1ea`）も `std::string` のコンストラクタ／`_M_construct` へ委譲し、後者は +0 に `this+16` を入れてから構築する SSO 形式である。
- `CString::Reserve(unsigned int)`（`0x254c0dc`）は `std::string::reserve` へ、`SetSize(int, char)`（`0x254c3f2`）は `std::string::resize` へそのまま委譲する。容量管理は `std::string` の機構に乗っている。

## 所有権

- バッファの所有者は、その `CString` を構築した側である。`SetText` の引数は `CString const&` であり、呼び出し側が所有するオブジェクトを借りているだけである。フックは所有者ではなく、勝手にバッファを解放・再確保してはならない。
- 現在の同一長置換は、所有者のバッファへ同じバイト数だけを上書きし、+0／+8／+16 のどれも変えないため、所有権と不変条件を壊さない。これが同一長に限って安全だった理由である。

## 容量

- 長さが15以下の文字列は通常 SSO で、容量は15である（終端NULを除く）。実機で置換が適用された `Back`（長さ4）と `Connect to ID`（長さ13）はどちらも15以下で、SSO 容量の範囲内だった可能性が高いが、現行フックは +16 を読まないため、実機の各呼び出しで SSO だったかヒープだったかは未確認である。
- ヒープ時は容量が +16 の `size_t` に入る。容量の判定手順は次のとおりで、これは今後の実装前提として記録するもので、今回の調査で実装はしていない。
  1. ヘッダを32バイト読む。
  2. データポインタがオブジェクトアドレス+16 と一致すれば容量15。
  3. 一致しなければ +16 の `size_t` を容量として読み、長さ以上であることを確認する。
- 容量を超える長さへの置換は、再確保が必要になる。再確保は所有者の `std::string` 状態（+0、+8、+16 の3要素）を一貫して書き換える必要があり、`const&` で借りたオブジェクトに対してフック側から行う安全性（アロケータの一致、例外、呼び出し側の想定）は証明できていない。よって容量超過の可変長置換は引き続き禁止とする。

## 寿命

- フックは元の `SetText` が実行される直前に動く。その時点で呼び出し側の `CString` は生存しており、データポインタ・長さ・終端NULを検証してから上書きする現在の手順は、寿命の範囲内である。
- `SetText`（`0x20d9da4`）の先頭処理は、第1引数について `(%rdx)` のデータポインタへ `strlen` をかけ、自オブジェクト +0x220 の文字列へ `_M_replace` でコピーする。第2・第3引数も同じ形式である。長さフィールド（+8）はこのコピーでは使われていない。
- したがって、置換後の文字列が表示に使われるのはこのコピー経由であり、呼び出し側 `CString` が戻り後に破棄されても表示は残る。逆に、戻り後に呼び出し側のバッファを書き換えても表示は変わらないはずだが、この点の実機確認は未実施である。
- 置換で長さを変える場合は、`SetText` が `strlen` で読むため終端NULの位置が実質的な長さを決める一方、`operator==` や `GetSize` など他の利用者は +8 を見る。両方を一致させないと、利用者ごとに異なる文字列に見える不整合が起きる。可変長置換では +8 と終端NULの同時更新が必須である。

## 実機観測との対応

- 既存トレース（`memory-bank/progress.md`）で `SetText` は MENU 画面で頻繁に呼ばれ、全件 `tid=1` だった。フックの再入防止（`setTextActive`）と合わせて、単一スレッドからの呼び出しが主であることは確認済みだが、全ての呼び出し経路が単一スレッドである証明にはならない。
- 実機ログ（2026-11-21 の smoke 実行を含む）で、同一長置換は長さ4と13の両マッピングで `result=applied` となり、EU4 は Exit ボタンで正常終了した。これは同一長・容量内という前提と矛盾しない。

## 未確認事項

- 実機の各 `SetText` 呼び出しにおける容量の実測値（SSO／ヒープの別とヒープ容量）。判定にはヘッダ32バイト読み取りが必要で、現行フックには無い。
- 容量以内の可変長置換の実機確認。根拠は静的解析までで、表示・正常終了・他の利用者への影響は未検証である。
- 呼び出し側が `SetText` の戻り後に同じ `CString` を再利用するかどうか。再利用される場合、フックが書き換えた内容が呼び出し側の後続処理にも見える点は、同一長置換でも変わらない既存の前提である。

## 次の作業への制約

1. 可変長置換を実装する場合は、まずヘッダ読み取りを32バイトへ広げ、容量をログへ出す変更だけを先に行い、実機で容量の実測を集める。
2. 置換は「新しい長さが容量以下」の場合に限る。+8 の長さと終端NULを同時に更新し、データポインタと +16 は変えない。
3. 容量を超える置換は、この文書の「容量」の節の未証明事項が解けるまで実装しない。
